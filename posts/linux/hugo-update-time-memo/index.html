Hugo 文章「更新于」时间机制与修改文章操作备忘

内部备忘（永不发布）：本站文章更新时间如何显示、手动改文章与蜜改文章的机制差异、如何查看验证。

⚠️ 本文是内部操作备忘，draft = true 永不发布。随时可回查，照着操作即可。

最后核验：2026-08-06（蜜与小哥共同确认机制正确）。

一、背景：为什么会有这篇文章

2026-08-01 本站曾出现全站文章正文都显示「更新于 2026年8月1日」的假象。根因有两层：

  1. 站点曾开启 enableGitInfo: true——Hugo 0.131 实测：开启后 .Lastmod（“更新于"数据源）默认取 git 最后提交时间，front matter 里手写的 lastmod 字段反而会被忽略（Hugo 默认配置 Lastmod: [':git', 'lastmod', ...]，git 优先）。
  2. 8月1日有一次批量提交，给 134 篇文章的 front matter 统一加了 pinned = false 模板字段 → 这 134 篇的 git 最后提交时间全部变成 8月1日 → 全站"更新于 8月1日”。

修复方案：关掉 enableGitInfo，改用 front matter lastmod + 文件修改时间兜底。机制细节见下。

二、现在的机制（怎么决定"更新于"显示什么）

hugo.yaml 中的配置：

frontmatter:
  lastmod:
    - lastmod        # ① 优先：front matter 里的 lastmod 字段
    - :fileModTime   # ② 兜底：没有 lastmod 就用文件修改时间（mtime）

模板 layouts/_default/single.html 的显示逻辑：

{{- if ne (.Date.Format "2006-01-02") (.Lastmod.Format "2006-01-02") }}
  <time class="updated">更新于 {{ .Lastmod.Format "2006年1月2日" }}</time>
{{- end }}

即：只有当"更新日期 ≠ 发布日期"时才显示"更新于"。没更新过的文章不显示，逻辑自洽。

两类文章的现状

类型 数量 特点
有 lastmod 字段 49 篇 曾经有真实内容更新，lastmod 写的是真实更新时间
无 lastmod 字段 91 篇 从未实质更新过；靠 mtime 兜底，mtime 已恢复为各自的发布日期 → 不显示"更新于"

三、你（小哥）手动改文章的操作方法

情况 A：改的是"无 lastmod 字段"的文章（91 篇）

什么都不用写。 机制自动工作：

  1. 用编辑器打开 content/posts/<分类>/<slug>/index.md
  2. 修改正文 → 保存
  3. 保存那一刻，文件的修改时间（mtime）自动变成现在
  4. Hugo 构建/预览后，页面自动显示「更新于 今天」

注意：不要把 mtime 弄丢的场景——比如 git clone、git pull、批量脚本 touch 都会改 mtime。所以 git 操作后如发现日期不对，参考第五节修复。

情况 B：改的是"有 lastmod 字段"的文章（49 篇）

需要手动把 lastmod 改成当天。 因为 lastmod 字段优先级最高，只要字段还在，mtime 就被忽略。

打开文章，在 front matter 的 date 行下面找/加一行：

+++
date = '2026-05-24T00:00:00+08:00'
lastmod = '2026-08-06'    # ← 改成修改当天
draft = false
+++
  • 站内统一 TOML 格式（+++ 包裹），写法：lastmod = '2026-08-06'
  • 个别旧文章是 YAML（--- 包裹），那种写法是 lastmod: 2026-08-06

判断文章属于哪类（10 秒查询）

grep -l '^lastmod' /home/hermesuser/codex/hugo/content/posts/*/*/index.md

输出里出现的就是"有 lastmod"的 49 篇；没出现的（91 篇）改正文保存即可。

四、蜜（AI 助手）改文章的机制

蜜改文章用的是 write_file / patch 工具，已实测验证：

场景 是否自动 说明
改"无 lastmod"文章 ✅ 自动 write_file / patch 都会更新文件 mtime → 兜底自动生效
改"有 lastmod"文章 ✅ 蜜会主动改 蜜的工作流程会自动把 lastmod 更新为当天，不用你管

结论：文章修改交给蜜最省心，你只负责看结果。

六、手动发布文章（上线）方法

本站架构：源码仓库（/home/hermesuser/codex/hugo，私有，存 Markdown 原文）→ 构建 → 发布仓库（/home/hermesuser/codex/hugo/public，公开，GitHub Pages 部署）。发布 = 在 public/ 里构建 + 提交 + 推送。

完整发布命令（复制即用）

在 /home/hermesuser/codex/hugo 目录下依次执行：

cd /home/hermesuser/codex/hugo

# ① 先拉取最新发布仓库（防止多人协作冲突，必须）
git -C public pull --rebase origin main

# ② 草稿安全检查（强制！防止草稿旧产物被推上线）
grep -rl 'draft = true' content/posts/ --include='index.md' | while read f; do
  dir=$(dirname "$f" | sed 's|content/||')
  [ -d "public/$dir" ] && { echo "⚠️ 草稿残留 public/$dir"; rm -rf "public/$dir"; }
done

# ③ 正式构建（--minify 压缩，--gc 清理；本站 700+ 页约 60s，用大 timeout）
hugo --minify --gc

# ④ 检查构建结果（确认目标文章生成了 HTML）
ls public/posts/<分类>/<slug>/index.html

# ⑤ 提交并推送发布仓库（触发 GitHub Pages 部署）
git -C public add -A
git -C public commit -m "发布：<文章标题>"
GIT_SSH_COMMAND="/home/hermesuser/.hermes/scripts/git-ssh-wrapper.sh" git -C public push origin main

# ⑥ 部署后验证（GitHub Pages 异步部署，等 30-90 秒）
curl -s -m 5 -H "Cache-Control: no-cache" "https://purodn.tk/posts/<分类>/<slug>/" | grep -c "<正文里的独有短语>"

举例说明（完整示例）

假设你写好了一篇新文章 content/posts/linux/my-new-post/index.md（draft 已改 false），要发布上线：

cd /home/hermesuser/codex/hugo

# ① 拉最新发布仓库
git -C public pull --rebase origin main

# ② 草稿检查（本文自身就是草稿，会提示残留——正是防它的）
grep -rl 'draft = true' content/posts/ --include='index.md' | while read f; do
  dir=$(dirname "$f" | sed 's|content/||')
  [ -d "public/$dir" ] && { echo "⚠️ 草稿残留 public/$dir"; rm -rf "public/$dir"; }
done
# 输出示例：⚠️ 草稿残留 public/posts/linux/hugo-update-time-memo（这是正常的，因为那篇是永久草稿）

# ③ 构建（等约 60 秒）
hugo --minify --gc
# 输出结尾示例：Total in 58s

# ④ 确认文章 HTML 已生成
ls public/posts/linux/my-new-post/index.html
# 输出示例：public/posts/linux/my-new-post/index.html

# ⑤ 提交推送
git -C public add -A
git -C public commit -m "发布：我的新文章"
GIT_SSH_COMMAND="/home/hermesuser/.hermes/scripts/git-ssh-wrapper.sh" git -C public push origin main
# 输出示例：To github.com:hanigege/purodn.tk.git  abc1234..def5678  main -> main

# ⑥ 等 30-90 秒后验证线上是否真的上线
curl -s -m 5 -H "Cache-Control: no-cache" "https://purodn.tk/posts/linux/my-new-post/" | grep -c "我的新文章里的独特句子"
# 输出 1+ 说明上线成功；输出 0 说明没部署好或内容不对，再等一会重试

发布注意事项（血泪教训）

  1. 草稿检查是强制第一步：Hugo 增量构建不会删除 public/ 里草稿的旧 HTML，git add -A 会把它们一起推上线。2026-08-05 曾因此把 14 篇草稿（含 sing-box 真实凭据备份）挂上公开站 3 天！
  2. 含凭据/私人信息的文章：必须 draft = true 且 发布前从 public/ 清除，否则视为泄露。
  3. 构建失败排查：先跑 hugo --destination /tmp/hugo-check-build --cleanDestinationDir --gc（不带 –minify，快）定位错误，修好再正式构建。
  4. GitHub Pages 部署是异步的：push 后 404 不代表失败，等 30-90 秒再验证；验证要 grep 正文独有短语，HTTP 200 不代表内容正确。
  5. 不要 push 源码仓库：源码只推 purodn.tk-source-code.git（私有），发布只推 purodn.tk.git（公开），两个仓库别搞混。

也可以让蜜代劳

跟蜜说一声"发布 XX 文章/推上去吧"，蜜会按上述流程完整执行（草稿检查 → 构建 → 推送 → 线上验证）。蜜还会用 purodn 一键脚本辅助（定义在 ~/.zshrc）。

快捷命令 purodn（2026-08-06 已加固）

在终端直接输入 purodn 即可一键发布。新版已内置全部安全措施：

  • ✅ 发布前 pull --rebase --autostash 拉最新（防多人冲突）
  • ✅ 草稿文章页检查（发现即删除，防草稿旧 HTML 上线）
  • ✅ 草稿 tag 聚合页检查（草稿专属 tag 整目录删；共享 tag 页内残留草稿链接也删页重建——这是 8月6日新发现的泄露面）
  • ✅ 构建后复查（文章页 + tag 页都不许有草稿）
  • ✅ hugo --minify --gc 构建
  • ✅ SSH wrapper 推送（本机 OpenSSH 9.9 兼容，裸 git push 会报 unable to fork）

脚本位置：/home/hermesuser/codex/hugo/scripts/purodn（.bashrc 的 purodn() 函数已改为调用此脚本，旧版内联逻辑已废弃，备份在 scripts/purodn.bak-20260806）。
