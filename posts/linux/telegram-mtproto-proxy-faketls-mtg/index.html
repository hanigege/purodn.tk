Telegram MTProto 代理 FakeTLS 完整教程：mtg 部署与客户端使用

一条主线七步部署 9seconds/mtg：查 IP 归属选伪装域名、生成 ee 密钥、docker run 与 compose 两种启动、mtg doctor 自检、导出代理链接，以及 Telegram 客户端三种使用方式。附双栈与动态 IP DDNS 配置，全部真机实测。

Telegram 官方支持一种叫 MTProto Proxy 的自建代理协议。它最大的好处是客户端原生支持：不用装任何第三方 App，把一条 https://t.me/proxy?... 链接发给别人，点一下就自动配好了。

但裸 MTProto 特征明显，容易被识别封锁，所以现在能用的方案都必须开 FakeTLS（TLS 伪装）。

这篇教程的路线：

  1. FakeTLS 与选型 — 原理，三款代理怎么选
  2. 部署 — 一条主线七步走完，不用做选择
  3. 导出代理链接 — 一条命令
  4. 客户端怎么用 — 三种方式（很多教程漏掉的一步）

后面是选读：识别 FakeTLS 链接、进阶配置、实战验证记录，以及附录里的其他部署方式（simple-run / compose / systemd / 双栈 / 动态 IP DDNS）。

💡 全文命令都在真机跑过，输出都是真的。踩过的坑写在对应位置和文末「实战验证」里。

一、FakeTLS 与选型

FakeTLS 解决什么问题

普通 MTProto 代理的握手包不像任何常见协议，很容易被流量分析打上标签。

FakeTLS 的做法是：把 MTProto 流量包装成一次看起来完全正常的 TLS 握手，握手里明文携带的 SNI（Server Name Indication，目标域名）写成一个真实存在的大站，比如 cloudflare.com。

mtg 在此之上还多做两件事：

  • 域名前置（Domain Fronting）：如果来的请求密钥不对（比如探测器扫你的端口），mtg 不断开连接，而是把请求原样转给你伪装的那个真实网站，再把真实响应字节对字节回给对方。探测者看到的就是一个正常网站。
  • Doppelganger（分身）：模仿真实网站 TLS 数据包的时序和分块特征，让流量在统计学上也难以区分。默认自带 ok.ru 的统计数据，一般不用动。

三款代理对比

① 最推荐：9seconds/mtg（Go 语言版）

  • 仓库：https://github.com/9seconds/mtg
  • 本文实测版本：v2.2.8，Docker 镜像 nineseconds/mtg:2

作者在重构到 v2.x 后原生全面支持 FakeTLS 和链路优化，是目前维护最好、性能最好的单文件 / Docker 工具，能撑约 1~2 万并发连接。

优点：

  • 单个静态二进制，或一行 docker run 就能跑
  • 只支持 FakeTLS，v2 直接禁用了旧的 simple / secured 模式，不给你配错的机会
  • 自带 mtg doctor 自检、mtg access 出链接
  • 支持 SOCKS5 上游链式代理（出站可再套 Trojan / sing-box / v2ray）
  • 支持 IP 黑名单、防重放攻击、Proxy Protocol v1/v2

取舍（作者故意这么设计的）：

  • ⚠️ 只支持单个密钥，无多用户管理。要多密钥用 fork mtg-multi
  • ⚠️ v2 完全移除 adtag（推广频道）。要 adtag 用 v1 分支，或改用 telemt
  • ⚠️ 没有 Web 面板，作者明确表示不做

分支别选错：

分支 用途
stable 推荐，master 的稳定快照
master 开发前沿，可能有破坏性变更
v2 v2.x 开发线，目前等同 master
v1 仅维护模式，唯一有 adtag 的分支

② Docker 一键部署版

  • yurykovshov/mtproto-proxy
  • alexbers/mtprotoproxy（Python 实现，也支持 FakeTLS）
  • iShift/docker-compose-mtproxy

这类项目是对 mtg 或 C 版的一键脚本 / 容器封装，内置自动生成 ee 前缀密钥和域名伪装的逻辑，适合完全不想碰配置文件的人。

  • ✅ 一条命令跑完，密钥和链接自动打印
  • ⚠️ 版本滞后于上游，出问题要同时看封装脚本和上游两层代码。选之前看仓库最后提交时间，超过一年没动的别用

③ 官方 C 语言版：TelegramMessenger/MTProxy

  • 仓库：https://github.com/TelegramMessenger/MTProxy

  • ✅ 官方出品，性能极高，adtag 的原生实现

  • ⚠️ 要自己编译（依赖 openssl-devel、zlib-devel），命令行参数很多，比 mtg 繁琐得多。官方仓库更新极慢，FakeTLS 靠社区补丁

一句话选型

你的情况 选什么
自己或小圈子用，想最省心 9seconds/mtg v2
完全不想碰配置文件 Docker 一键封装版
需要 adtag 推广频道 mtg v1 或 telemt
需要多用户多密钥 mtg-multi fork

二、部署（一条主线走完）

下面这条流程是真机从零跑通的完整过程，照着抄就行，不用做任何选择。用 Docker + 配置文件，因为这条路能用 mtg doctor 自检、mtg access 自动出链接，出问题好查。

（不想用配置文件、想一条命令搞定，或者要 compose / systemd / 双栈 / 动态 IP，见文末「附录：其他部署方式」。）

第 1 步：确定伪装域名

FakeTLS 要假装访问一个真实网站，这个域名不能乱选。

很多教程直接抄 google.com——这是坏例子，作者本人在 README 里说过：运营商很容易查出你的 IP 不属于 Google 的网段，一对不上就露馅。

正确做法是选和你服务器 IP 归属同一家的域名。先查你的 IP 属于谁：

curl -s https://ipinfo.io/$(curl -s ifconfig.co) | grep -E 'org|hostname'

本文实测服务器的真实输出：

  "hostname": "192-227-236-209-host.colocrossing.com",
  "org": "AS36352 HostPapa",

org 是 HostPapa、hostname 带 colocrossing.com，所以伪装域名就选 www.colocrossing.com。

这个选择好在哪：www.colocrossing.com 解析到 198.23.210.28，和本文服务器 192.227.236.209 同属 ColoCrossing 网段。审查方看到「ColoCrossing 的 IP 在访问 ColoCrossing 官网」，完全合理。

上面的要说明一下，这个只针对墙外的vps的测试方法，墙内的话：

在墙内家宽环境下，FakeTLS 伪装域名该选什么？ 完全不需要填写联通自己的域名，直接选择国际公认、流量巨大的大厂域名是效果最好、最稳定的。

优先推荐使用以下域名来生成 mtg 的 Secret：

cloudflare.com（最推荐，节点和流量极其庞大，防封效果最好）

azure.microsoft.com 或 microsoft.com（微软大厂域名）

aws.amazon.com（亚马逊 AWS）

dl.google.com

如何用这个域名生成 Secret？ 直接在终端运行 mtg generate-secret，把伪装域名设为 cloudflare.com 即可：

docker run --rm nineseconds/mtg:2 generate-secret --hex cloudflare.com

这样生成的以 ee 开头的 Secret（里面已经包含了 cloudflare.com 的十六进制编码）：

客户端在建立 TLS 握手时，DPI 看到的目标域名是 cloudflare.com，不会盲目拦截。

Telegram 客户端与你的服务器握手成功后，就能正常传输加密数据。

按你自己的结果对应着选：

org / hostname 显示 伪装域名用
ColoCrossing / HostPapa www.colocrossing.com
DigitalOcean digitalocean.com
Vultr vultr.com
Hetzner hetzner.com
Linode / Akamai linode.com

⚠️ 密钥等于密码，泄露了别人就能白用你的代理。别发到公开地方。

第 3 步：写配置文件

mkdir -p ~/data/docker_data/mtg && cd ~/data/docker_data/mtg
nvim config.toml

内容只要三段：

secret = "ee4a7e409b8984becd8117b5729e08e78f7777772e636f6c6f63726f7373696e672e636f6d"
bind-to = "0.0.0.0:3128"

[network]
dns = "https://223.5.5.5"

三行分别是什么：

配置项 说明
secret 上一步生成的密钥
bind-to 容器内监听地址。主机部分必须是字面 IP，写域名会报 host is not an IP address。这个 3128 不是客户端连的端口
dns DNS 解析器。必须写，理由见下

⚠️ dns 这一行别省，这是最容易翻车的地方。 mtg 默认用 1.1.1.1 做 DNS-over-HTTPS，很多服务器（尤其墙内）访问不到，会导致域名前置直接失效，日志刷：

{"level":"warn","logger":"proxy","error":"dial tcp: lookup ...: i/o timeout","message":"cannot dial to the fronting domain"}

坑在于容器显示 Up、端口也在监听，看起来一切正常，但客户端就是连不上。写成 dns = "https://223.5.5.5"（阿里 DoH）或 https://8.8.8.8 即可。

顺带一提：mtg v2.1.12 之前这个选项叫 doh-ip，老教程抄的是旧名字，两个不能同时写。

第 4 步：启动

两种启动方式，效果完全一样，选一个。想长期维护建议用 compose（配置都写在文件里，不用记命令）。

方式一：docker run 一条命令

docker run -d -v $PWD/config.toml:/config.toml -p 27777:3128 --name mtg --restart always nineseconds/mtg:2

真实输出（容器 ID）：

7a2465b9bbf5142165292a6ba21c475ac7508d111290c99930a0ca2620534690

方式二：docker-compose（推荐长期用）

在同一个目录（~/data/docker_data/mtg）里再建一个文件：

nvim docker-compose.yml

内容：

services:
  mtg:
    image: nineseconds/mtg:2
    container_name: mtg
    restart: always
    volumes:
      - ./config.toml:/config.toml:ro
    ports:
      - "27777:3128"

启动：

docker compose up -d

💡 密钥不在 compose 文件里，它在 config.toml 里。compose 只负责把配置文件挂进容器（:ro 是只读挂载，更安全）。所以要改密钥只动 config.toml，compose 文件不用碰。

compose 的日常操作：

操作 命令
启动 docker compose up -d
停止 docker compose down
重启（改完配置后） docker compose restart
看状态 docker compose ps
看日志 docker compose logs --tail 50
升级镜像 docker compose pull && docker compose up -d

两种方式都要注意的端口问题

-p 27777:3128（或 compose 里的 "27777:3128"）是全流程最容易搞混的一处：

  • 左边 27777 = 客户端要连的宿主机端口，自己定，后面拼链接用这个
  • 右边 3128 = 容器内端口，要和 config.toml 里 bind-to 的端口一致

💡 端口优先选 443。高位端口跑 TLS 流量本身是异常特征，伪装效果打折。443 没被占用就改成 443:3128，配置文件不用动。本文用 27777 只是因为测试机 443 已占用。

顺手把 IPv6 也支持上（可选）

上面的配置只监听 IPv4。服务器有 IPv6 的话，把 config.toml 里的 bind-to 改一个字就同时支持两种客户端：

secret = "ee4a7e409b8984becd8117b5729e08e78f7777772e636f6c6f63726f7373696e672e636f6d"
bind-to = "[::]:3128"
prefer-ip = "prefer-ipv4"

[network]
dns = "https://223.5.5.5"

改动只有两处：

配置项 作用
bind-to = "[::]:3128" [::] 是 IPv6 通配地址，Linux 下同时覆盖 IPv4 和 IPv6（中括号不能省，因为 IPv6 地址自带冒号，不加括号分不清端口分隔符）
prefer-ip = "prefer-ipv4" mtg 出站连 Telegram 时优先用 IPv4。默认是 prefer-ipv6，但 IPv6 是隧道或质量不好时反而变慢，所以一般写 prefer-ipv4

改完重启，本文实测 docker ps 输出确认双栈映射生效：

mtg   Up 4 seconds   0.0.0.0:27777->3128/tcp, [::]:27777->3128/tcp

ss -tln | grep 27777 也能看到两条：

LISTEN 0  4096   0.0.0.0:27777   0.0.0.0:*
LISTEN 0  4096      [::]:27777      [::]:*

⚠️ Docker 的 bridge 网络默认不转发 IPv6 外部流量。上面这样配，容器内和端口映射层面是双栈了，但要让公网 IPv6 客户端真正连进来，最省事的办法是改用 host 网络（compose 里加 network_mode: host，同时去掉 ports: 段，此时 bind-to 的端口就是客户端连的真实端口）。详细说明和另一种开 Docker IPv6 的办法见文末附录「IPv4 + IPv6 双栈」。

💡 只有 IPv4 的服务器直接用 bind-to = "0.0.0.0:3128" 就好，别配双栈，白折腾。

第 5 步：自检

docker exec mtg /mtg doctor /config.toml

真实输出：

Deprecated options
  ✅ All good
Time skewness
  ✅ Time drift is -9.520119ms, but tolerate-time-skewness is 3s
Validate native network connectivity
  ✅ DC 1
  ✅ DC 2
  ✅ DC 3
  ✅ DC 4
  ✅ DC 5
  ✅ DC 203
Validate fronting domain connectivity
  ✅ www.colocrossing.com:443 is reachable

  ❌ Hostname www.colocrossing.com is resolved to "198.23.210.28" addresses, not 192.227.236.209

最后那个 ❌ 是正常的，不用管。

这一项检查的是「伪装域名解析的 IP」是否完全等于你服务器的 IP。要它变绿，等于要求你拥有 www.colocrossing.com 这个域名并把它解析到你自己机器上——不可能做到。只要你是拿别人的域名做伪装，这项就必然是 ❌，跟配置对不对没关系。

真正要看的是它上面两项，这两项必须 ✅：

检查项 意义 ❌ 了怎么办
native network connectivity 6 个 DC 你的服务器能连上 Telegram 某个 DC ❌ 说明到该数据中心不通，可能被墙，考虑配 SOCKS5 上游
fronting domain connectivity 域名前置能正常工作 ❌ 先查 dns 那一行是不是没写（第 3 步的坑），再考虑换域名
Time skewness 服务器时间准 ❌ 执行 timedatectl set-ntp true；出现 ‼️ cannot access ntp pool 是没测成（容器 UDP 123 被拦），不是时间不对，宿主机 timedatectl status 显示 synchronized: yes 就没事
Deprecated options 没用废弃选项 ❌ 把顶层 domain-fronting-* 改写进 [domain-fronting] 段

第 6 步：放行端口

sudo ufw allow 27777/tcp

⚠️ 云服务器还要去厂商控制台的安全组里放行同一个端口，只改服务器本地防火墙不够。

第 7 步：验证域名前置真的在工作

用 curl 冒充探测器连你的代理，正常情况应该收到伪装网站的真实响应：

curl -sk --max-time 15 https://192.227.236.209:27777/ -H "Host: www.colocrossing.com" -D- -o /dev/null | head -6

本文实测输出：

HTTP/1.1 200 OK
Date: Thu, 30 Jul 2026 02:08:37 GMT
Server: Apache
Last-Modified: Thu, 30 Jul 2026 01:13:40 GMT
Cache-Control: max-age=0
Expires: Thu, 30 Jul 2026 02:08:37 GMT

返回的是 ColoCrossing 官网真实的 Apache 200 响应——说明域名前置生效了：不知道密钥的探测者扫到你这个端口，看到的就是个普通网站，而不是代理。这就是 FakeTLS 的核心价值。

💡 不带 Host 头直接 curl 会返回 400，这是正常的（SNI 不匹配被真实网站自己拒了）。 返回 000 或超时才是有问题，八成是第 3 步的 dns 没写。

⚠️ -p 27777 必须加！ 不加的话输出的 port 会是配置文件里的 3128（容器内端口），拿那条链接客户端连不上。这个坑很多人踩。

字段 用途
tme_url 最常用，https://t.me/proxy?... 形式，发到聊天里能点

服务器连不上 ifconfig.co 时（ip 字段是空的或错的），手动指定：

docker exec mtg /mtg access -p 27777 -i 你的公网IP /config.toml

四、客户端怎么用（三种方式）

方式一：点链接（最简单，推荐）

把 tme_url 那条链接发到任意 Telegram 聊天窗口——发给自己的「Saved Messages / 收藏夹」最方便——然后点它：

https://t.me/proxy?port=27777&secret=7kp-QJuJhL7NgRe1cp4I5493d3cuY29sb2Nyb3NzaW5nLmNvbQ&server=192.227.236.209

Telegram 弹出确认框：

启用此代理？/ Enable this proxy? 192.227.236.209:27777

点「启用代理 / Enable Proxy」，完事。服务器、端口、密钥全自动填好。

方式二：扫二维码（配到手机上）

在电脑浏览器打开 access 输出里的 tme_qrcode 那条链接，会显示一张二维码，手机 Telegram 扫一下就配好了。

适合「在电脑上部署完，要配到手机」的场景，省得把长链接传来传去。

方式三：手动填（前两种都不行时）

各平台菜单路径：

  • Android：设置 → 数据和存储 → 代理设置 → 添加代理 → MTProto 代理
  • iOS：设置 → 数据与存储 → 代理 → 添加代理 → MTProto
  • 桌面版（Windows / macOS / Linux）：设置 → 高级 → 连接类型 → 使用自定义代理 → 添加代理 → MTProto

填三个字段：

字段 填什么 本文示例
Server / 服务器 服务器公网 IP 192.227.236.209
Port / 端口 -p 冒号左边那个数字 27777
Secret / 密钥 access 输出的 base64（或 hex，都认） 7kp-QJuJhL7NgRe1cp4I5493d3cuY29sb2Nyb3NzaW5nLmNvbQ

⚠️ 类型必须选 MTProto，别填到 SOCKS5 那一栏——填错栏永远连不上，这是最常见的错。

怎么确认连上了

  • 代理设置页面里，该条目下方显示「已连接 / Connected」
  • 顶部标题栏不再转圈显示「连接中… / Connecting…」
  • 随便打开个频道，消息能正常刷新

连不上怎么查（按这个顺序）

  1. 端口对不对——链接里的 port 是不是 -p 冒号左边那个数字？mtg access 忘加 -p 的话这里必错
  2. 防火墙 / 安全组——本地 sudo ufw allow 27777/tcp，以及云厂商控制台的安全组
  3. 容器活着吗——docker ps --filter name=mtg，STATUS 要是 Up
  4. 看日志——docker logs mtg。刷 cannot dial to the fronting domain 就是 dns 那行没写
  5. 重跑第 7 步的 curl 验证——服务端自己能不能通
  6. 类型选错了吗——手动填的时候是不是填到 SOCKS5 栏了

分享给别人时注意

  • 链接里含完整密钥，给出去等于给了账号
  • mtg v2 只支持单个密钥，做不到给不同人不同密钥（要这功能用 mtg-multi fork）
  • 别公开传播。作者原话：代理应该「fly under the radar」，一旦被大范围分享，等着 IP 被封

日常维护

改完配置重启：

docker restart mtg

换密钥（比如泄露了）：

# 1. 生成新密钥
docker run --rm nineseconds/mtg:2 generate-secret --hex www.colocrossing.com
# 2. 填进 config.toml 的 secret
# 3. 重启
docker restart mtg
# 4. 重新导出链接发给用户（旧链接立即失效）
docker exec mtg /mtg access -p 27777 /config.toml

看日志：

docker logs --tail 50 mtg

💡 docker logs 是空的不是故障。mtg 默认 debug = false，正常运行几乎不打日志。要详细日志在 config.toml 里加 debug = true 再重启。

五、如何识别一个代理链接是否开启了 FakeTLS

拿到别人给的 tg://proxy?... 或 https://t.me/proxy?...，只看 secret 就能判断：

密钥形态 类型 说明
32 位十六进制，如 d41d8cd98f00b204e9800998ecf8427e 普通 MTProto 无任何伪装，最容易被封
以 dd 开头（34 位 hex） 混淆模式（secured） 有随机填充，但没有 TLS 伪装
以 ee 开头，后面附加 hex 编码的伪装域名 FakeTLS ✅ 有 TLS 伪装，最抗检测

ee 密钥的结构：

ee 4fab7465717aff1924b27420437817ef 636c6f7564666c6172652e636f6d
│  └── 32位 hex = 16 字节真实密钥 ──┘ └─── hex 编码的伪装域名 ───┘
└─ FakeTLS 标记

把末尾那段 hex 解码，就知道它伪装成了什么网站：

echo -n "636c6f7564666c6172652e636f6d" | xxd -r -p
cloudflare.com

一条命令从完整密钥里剥出域名（跳过前面 ee + 32 位密钥共 34 个字符）：

echo "ee4fab7465717aff1924b27420437817ef636c6f7564666c6172652e636f6d" | cut -c35- | xxd -r -p
cloudflare.com

Base64 格式的密钥怎么判断？

客户端链接里常见 Base64（更短），比如 7k-rdGVxev8ZJLJ0IEN4F-9jbG91ZGZsYXJlLmNvbQ。它和上面那串 hex 是同一个密钥。方法是解码转 hex，看是不是 ee 开头：

python3 -c "
import base64, binascii
s = '7k-rdGVxev8ZJLJ0IEN4F-9jbG91ZGZsYXJlLmNvbQ'
raw = base64.urlsafe_b64decode(s + '=' * (-len(s) % 4))
h = binascii.hexlify(raw).decode()
print('hex     :', h)
print('FakeTLS :', h.startswith('ee'))
print('伪装域名:', binascii.unhexlify(h[34:]).decode(errors='replace'))
"

本文实测输出：

hex     : ee4fab7465717aff1924b27420437817ef636c6f7564666c6172652e636f6d
FakeTLS : True
伪装域名: cloudflare.com

💡 用 Python 而不是 base64 -d 是因为 Telegram 用的是 URL-safe Base64（- 和 _ 代替 + 和 /）且省略了末尾的 = 填充，base64 -d 会直接报错。上面的脚本已经处理好这两点。

额外的判断经验：FakeTLS 代理端口通常是 443。如果看到 ee 开头的密钥却配了个奇怪的高位端口，伪装效果会打折——「TLS 流量走非 443 端口」本身就是异常信号。（本文为避开本机已占用端口用了 27777，生产环境建议 443。）

六、进阶配置

完整选项参考仓库的 example.config.toml，每项都有注释，那个文件本身就是配置文档。挑几个实用的：

# 最大并发连接数，默认 8192
concurrency = 8192

# IP 协议偏好：prefer-ipv6(默认) / prefer-ipv4 / only-ipv6 / only-ipv4
prefer-ip = "prefer-ipv6"

# 服务器访问不了 ifconfig.co 时手动指定公网 IP，
# 让 mtg access 和 mtg doctor 能正常工作。
# 想让 mtg access 输出 IPv6 链接，public-ipv6 必须手动写
# public-ipv4 = "203.0.113.45"
# public-ipv6 = "2001:db8::1"

# 容忍的时间偏差，默认 3s
tolerate-time-skewness = "5s"

# 排障时打开，日志变得非常详细
debug = false

[network]
# DNS 解析器，默认 https://1.1.1.1。墙内机器务必改掉。
# 支持 DoH(https://)、DoT(tls://)、UDP(udp:// 或裸 IP)
dns = "https://223.5.5.5"

伪装域名的 DNS 在你的网络里被污染或封锁时，可以直接指定要连的 IP，SNI 仍用原域名：

[domain-fronting]
ip = "104.16.132.229"
port = 443

⚠️ 顶层的 domain-fronting-port、domain-fronting-ip、domain-fronting-proxy-protocol 已废弃。老教程还在用它们，现在应写进 [domain-fronting] 段。mtg doctor 第一项 Deprecated options 就是查这个的。

让 Doppelganger 模仿你自己选的站，而不是默认的 ok.ru：

[defense.doppelganger]
urls = [
  "https://example.com/index.html",
  "https://example.com/contacts.html",
]

规则：必须 HTTPS、尽量同域名、2~3 个够了（一轻一重页面）、必须服务器能直连。作者原话：「如果你不确定这是干什么的，就什么都别动，默认值已经很好」。

七、实战验证

测试环境

  • 服务器 ColoCrossing（AS36352 HostPapa），公网 IP 192.227.236.209
  • Docker 29.2.1，镜像 nineseconds/mtg:2，实际版本 v2.2.8
  • 伪装域名 www.colocrossing.com，端口映射 27777 → 容器 3128

主线七步的实测结果

步骤 结果
查 IP 归属 ✅ org: AS36352 HostPapa，hostname: 192-227-236-209-host.colocrossing.com
生成密钥 ✅ 输出 ee4a7e40...636f6d，ee 前缀 + 域名 hex 结构正确
写配置 + 启动 ✅ 容器 ID 7a2465b9bbf5...，STATUS Up
mtg doctor ✅ 6 个 DC 全通、fronting domain reachable；SNI-DNS match ❌（必然，见下）
端口可达性（外网测） ✅ 27777 端口开放
域名前置（外网测） ✅ HTTP/1.1 200 OK + Server: Apache，返回 ColoCrossing 官网真实响应
mtg access -p 27777 ✅ 输出端口正确的 tme_url / tg_url / 二维码链接
compose 方式启动（挂载 config.toml） ✅ 与 docker run 等效，容器 Up
双栈 bind-to = "[::]:3128" ✅ docker ps 显示 0.0.0.0:27777->3128/tcp, [::]:27777->3128/tcp，ss -tln 两条监听，前置返回 200

踩到过的坑与根因

  1. 默认 DoH 1.1.1.1 不通导致域名前置全挂（最重要的一个） 报错原文：

    {"level":"warn","logger":"proxy","error":"dial tcp: lookup cloudflare.com: i/o timeout","message":"cannot dial to the fronting domain"}

    curl 探测返回 000。根因：mtg 默认用 1.1.1.1 做 DNS-over-HTTPS，测试机访问不到，域名解析超时。解法：config.toml 写 dns = "https://223.5.5.5"，或 simple-run 加 -n 223.5.5.5。 迷惑点：容器 docker ps 显示 Up、端口在 LISTEN，看着完全正常，只有翻日志才能发现。

  2. Validate SNI-DNS match 必然 ❌，不是配错 报错原文：Hostname www.colocrossing.com is resolved to "198.23.210.28" addresses, not 192.227.236.209。 根因：这项要求伪装域名解析的 IP 等于服务器 IP，除非域名是你自己的且解析到本机，否则不可能满足。不影响功能——后续外网 curl 前置测试拿到了真实的 200 响应。

  3. mtg access 不加 -p 输出的端口是错的 不加时输出配置文件里 bind-to 的容器内端口（3128），拿那条链接客户端连不上。解法：mtg access -p 27777。

  4. bind-to / public-ipv4 / access -i 都不接受域名 实测报错：host is not an IP address / incorret ip ...（作者拼写错误，原文如此）/ --ipv4: invalid IP address。但不影响用 DDNS，见附录动态 IP 一节。

  5. docker logs 空的不是故障 mtg 默认 debug = false，正常运行几乎不打日志。要日志加 debug = true 重启。

  6. 本机 DNS 被污染会误导判断 测试机 getent hosts colocrossing.com 返回 2001:2::dd5（IETF 保留的文档测试地址段），是污染结果。用公共 DoH 复核才拿到真实的 198.23.210.28：

    curl -s "https://223.5.5.5/resolve?name=www.colocrossing.com&type=A"

八、运维小结

  • 端口优先选 443，最不显眼；本文用高位端口只是为了避开本机占用
  • DoH 一定要设成你能访问的，这是墙内机器最容易翻车的地方
  • 伪装域名与 IP 归属要对得上，最容易忽略又最影响存活时间
  • 有 IPv6 就配上双栈（bind-to = "[::]:443" + public-ipv6），Docker 场景直接用 --network host 最省事
  • 长期维护用 compose，配置都在文件里，升级镜像一条 docker compose pull && docker compose up -d
  • 动态 IP 用 DDNS 域名：服务端不用改（bind-to 填 0.0.0.0、别写 public-ipv4），链接里 server 直接填域名，TTL 设 60 秒
  • 密钥不要公开发布，MTProto 代理适合小圈子
  • 改配置后重跑 mtg doctor，能挡掉大部分低级错误
  • 墙内环境单纯的 MTProto 代理生存期有限；作者推荐把 mtg 作为前端，出站再通过 SOCKS5 链到 Trojan / sing-box / v2ray 隧道
  • 更多建议见仓库的 BEST_PRACTICES.md

附录：其他部署方式

主线用的是「Docker + 配置文件」。下面几种按需选，不看也能把代理跑起来。

一、simple-run：一条命令，不要配置文件

simple-run 模式把密钥直接写在启动命令里，完全不需要配置文件：

docker run -d --name mtg --restart always -p 27777:3128 nineseconds/mtg:2 simple-run -n 223.5.5.5 0.0.0.0:3128 ee4a7e409b8984becd8117b5729e08e78f7777772e636f6c6f63726f7373696e672e636f6d

拆解一下这条命令，每一段都要看懂：

片段 作用
-p 27777:3128 27777 是客户端要连的宿主机端口（自己定），3128 是容器内 mtg 监听的端口
simple-run mtg 的子命令，表示不用配置文件
-n 223.5.5.5 DoH 服务器地址。建议加，原因见下方警告
0.0.0.0:3128 mtg 在容器内监听的地址，要和 -p 后面那个数字一致
ee4fab...636f6d 你第 1 步生成的密钥

⚠️ 这是本文实测踩到的坑，务必注意：不加 -n 参数时 mtg 默认用 1.1.1.1 做 DNS-over-HTTPS 解析。如果你的服务器访问不了 1.1.1.1（墙内机器基本都不通），域名前置会直接失败，日志里刷这个：

{"level":"warn","logger":"proxy","error":"dial tcp: lookup www.colocrossing.com: i/o timeout","message":"cannot dial to the fronting domain"}

表现是：容器状态正常 Up，端口也在监听，但 curl 探测时连不上、Telegram 也连不上代理。

解法：加 -n 223.5.5.5（阿里 DoH）或 -n 8.8.8.8，本文实测换成 223.5.5.5 后立刻正常。

⚠️ -n 参数背后的配置项名字变过：mtg v2.1.12 之前配置文件里用 doh-ip，之后改成了更通用的 dns（同时支持 DoH https://、DoT tls://、UDP udp:// 或裸 IP）。老教程里的 doh-ip = "1.1.1.1" 等价于现在的 dns = "https://1.1.1.1"。两个都写会冲突，官方注释明确说了「设置 dns 时请把 doh-ip 注释掉」。

多行写法更好读（复制时注意行尾反斜杠后面不能有空格）：

docker run -d \
  --name mtg \
  --restart always \
  -p 27777:3128 \
  nineseconds/mtg:2 \
  simple-run -n 223.5.5.5 0.0.0.0:3128 ee4a7e409b8984becd8117b5729e08e78f7777772e636f6c6f63726f7373696e672e636f6d

其他可用参数：

参数 含义 默认值
-c 最大并发连接数 8192
-t 网络超时 10s
-a 防重放缓存大小 1MB
-i IP 偏好 prefer-ipv6
-p 域名前置端口 443
-d debug 模式，日志变详细 关

⚠️ simple-run 的代价：因为没有配置文件，mtg access 和 mtg doctor 这两个命令都用不了（它们都必须传配置文件路径，不传会报 mtg: error: expected "<config-path>"）。代理链接需要手动拼，方法见第三部分。

二、compose 里直接写密钥（不要 config.toml）

主线第 4 步已经讲了标准的 compose 用法（挂载 config.toml）。如果你连配置文件都不想建，可以用 command 让 compose 走 simple-run 模式，密钥直接写在 compose 文件里：

services:
  mtg:
    image: nineseconds/mtg:2
    container_name: mtg
    restart: always
    ports:
      - "27777:3128"
    command: >
      simple-run -n 223.5.5.5 0.0.0.0:3128
      ee4a7e409b8984becd8117b5729e08e78f7777772e636f6c6f63726f7373696e672e636f6d

这样目录里只有一个 docker-compose.yml，docker compose up -d 就跑起来了。

代价和上面的 simple-run 一样：mtg access / mtg doctor 都用不了（它们必须读配置文件），链接得自己拼。

💡 除非你特别讨厌多一个文件，否则建议还是用主线那种挂载 config.toml 的方式——能自检、能自动出链接，排障方便太多。

三、不用 Docker：二进制 + systemd

资源占用更小的话可以直接跑二进制。

拿二进制，三种途径任选：

# 途径一：从 Releases 下载对应架构压缩包
# https://github.com/9seconds/mtg/releases

# 途径二：有 Go 环境直接装
go install github.com/9seconds/mtg/v2@latest

# 途径三：源码编译（v2 用 mise，不是 make）
git clone https://github.com/9seconds/mtg.git
cd mtg && mise install && mise tasks run build

⚠️ 很多老教程还写 make build，v2 已换成 mise tasks run build（mise 是个工具版本管理器），照抄老命令会报找不到 Makefile。

放好文件。不用 Docker 时没有端口映射这层，bind-to 直接写客户端要连的真实端口：

sudo mv mtg /usr/local/bin/mtg && sudo chmod +x /usr/local/bin/mtg
sudo nvim /etc/mtg.toml
secret = "ee4a7e409b8984becd8117b5729e08e78f7777772e636f6c6f63726f7373696e672e636f6d"
bind-to = "0.0.0.0:443"

[network]
dns = "https://223.5.5.5"

写 systemd 服务：

sudo nvim /etc/systemd/system/mtg.service
[Unit]
Description=mtg - MTProto proxy server
Documentation=https://github.com/9seconds/mtg
After=network.target

[Service]
ExecStart=/usr/local/bin/mtg run /etc/mtg.toml
Restart=always
RestartSec=3
DynamicUser=true
LimitNOFILE=65536
AmbientCapabilities=CAP_NET_BIND_SERVICE

[Install]
WantedBy=multi-user.target

两个关键项别删：

  • AmbientCapabilities=CAP_NET_BIND_SERVICE——没有它，DynamicUser 起的非 root 进程绑不了 443 这种 1024 以下的端口，服务起不来
  • LimitNOFILE=65536——并发多时不至于耗尽文件描述符

启动并自检：

sudo systemctl daemon-reload
sudo systemctl enable --now mtg
systemctl status mtg --no-pager
mtg doctor /etc/mtg.toml

四、IPv4 + IPv6 双栈

前面所有例子的 bind-to = "0.0.0.0:3128" 只监听 IPv4，IPv6 客户端连不上。想两种都支持，要改三个地方。

第 1 处：bind-to 改成 [::]

bind-to = "[::]:3128"
写法 监听范围
"0.0.0.0:3128" 只有 IPv4
"[::]:3128" IPv4 + IPv6 双栈（Linux 默认 net.ipv6.bindv6only=0，IPv6 通配地址会自动兼容 IPv4）
"[::1]:3128" 只有本机 IPv6，别用，外面连不上

⚠️ 中括号不能省。TOML 里 IPv6 地址必须写成 [地址]:端口，因为 IPv6 地址本身含冒号，不加括号解析器分不清哪个冒号是端口分隔符。写成 "::3128" 会报错。

⚠️ 如果你的系统把 net.ipv6.bindv6only 改成了 1，[::] 就只监听 IPv6 了。查一下：sysctl net.ipv6.bindv6only，输出应该是 = 0。

第 2 处：prefer-ip 决定出站走哪个协议

这个选项管的是 mtg 连 Telegram 服务器时用 IPv4 还是 IPv6，和客户端连你没关系，两回事别搞混：

prefer-ip = "prefer-ipv6"

四个可选值：

值 含义
prefer-ipv6 两种都能用，优先 IPv6（默认值）
prefer-ipv4 两种都能用，优先 IPv4
only-ipv6 只用 IPv6 出站
only-ipv4 只用 IPv4 出站

💡 怎么选：服务器 IPv6 是原生的、质量好 → 留默认 prefer-ipv6。IPv6 是隧道的或者不稳 → 改 prefer-ipv4，否则 mtg 优先走 IPv6 反而变慢。完全没有 IPv6 → 写 only-ipv4，省掉每次都试一遍 IPv6 的开销。

第 3 处：public-ipv6 让 mtg access 输出 IPv6 链接

这一步是最容易漏的。mtg 默认通过访问 ifconfig.co 自动探测自己的公网 IP，探测不到 IPv6 就不会生成 IPv6 链接。手动指定就一定有：

public-ipv4 = "192.227.236.209"
public-ipv6 = "2001:db8::1"

这两个值去哪里查：

# 公网 IPv4
curl -s4 ifconfig.co

# 公网 IPv6（没输出说明服务器没有可用 IPv6）
curl -s6 ifconfig.co

也可以直接看网卡上的全局 IPv6 地址（scope global，不是 fe80:: 开头的链路本地地址）：

ip -6 addr show scope global | grep inet6

完整的双栈配置文件

secret = "ee4a7e409b8984becd8117b5729e08e78f7777772e636f6c6f63726f7373696e672e636f6d"

# 双栈监听：IPv4 和 IPv6 客户端都能连
bind-to = "[::]:3128"

# 出站连 Telegram 时优先用 IPv4（IPv6 质量不好时这样配）
prefer-ip = "prefer-ipv4"

# 手动指定公网地址，让 mtg access 能生成两种链接
public-ipv4 = "192.227.236.209"
public-ipv6 = "2001:db8::1"

[network]
dns = "https://223.5.5.5"

Docker 双栈额外要做的事

⚠️ 这里有个 Docker 层面的坑：容器里配好双栈还不够，Docker 默认的 bridge 网络不转发 IPv6。

最省事的办法是用 host 网络，绕开 Docker 的网络层：

docker run -d --name mtg --restart always --network host -v $PWD/config.toml:/config.toml nineseconds/mtg:2

用 --network host 时没有 -p 端口映射了，容器直接用宿主机网络，所以 bind-to 里的端口就是客户端要连的真实端口。想让客户端连 443 就写：

bind-to = "[::]:443"

compose 版：

services:
  mtg:
    image: nineseconds/mtg:2
    container_name: mtg
    restart: always
    network_mode: host
    volumes:
      - ./config.toml:/config.toml:ro

如果坚持用 bridge 网络，得先给 Docker 守护进程开 IPv6（改 /etc/docker/daemon.json 后重启 Docker）：

{
  "ipv6": true,
  "fixed-cidr-v6": "fd00:dead:beef::/64",
  "ip6tables": true
}
sudo systemctl restart docker

💡 建议：双栈场景直接用 --network host，比折腾 Docker IPv6 简单得多，性能也更好（少一层 NAT）。

验证双栈生效

配好后 mtg access 会同时输出 ipv4 和 ipv6 两段。本文实测输出：

{
  "ipv4": {
    "ip": "192.227.236.209",
    "port": 27782,
    "tme_url": "https://t.me/proxy?port=27782&secret=7kp-QJuJhL7NgRe1cp4I5493d3cuY29sb2Nyb3NzaW5nLmNvbQ&server=192.227.236.209"
  },
  "ipv6": {
    "ip": "2001:db8::1",
    "port": 27782,
    "tme_url": "https://t.me/proxy?port=27782&secret=7kp-QJuJhL7NgRe1cp4I5493d3cuY29sb2Nyb3NzaW5nLmNvbQ&server=2001%3Adb8%3A%3A1"
  },
  "secret": {
    "hex": "ee4a7e409b8984becd8117b5729e08e78f7777772e636f6c6f63726f7373696e672e636f6d",
    "base64": "7kp-QJuJhL7NgRe1cp4I5493d3cuY29sb2Nyb3NzaW5nLmNvbQ"
  }
}

看到 ipv6 这一段出现就说明配对了。 没配 public-ipv6 时这一段根本不会有。

💡 注意 IPv6 链接里的 server=2001%3Adb8%3A%3A1——%3A 是冒号 : 的 URL 编码。这是正确的，IPv6 地址在 URL 参数里必须编码，Telegram 客户端会自己解码。别手工把它改回冒号。

宿主机上确认端口两种协议都在听：

ss -tlnp | grep 443

双栈正常的话会看到 *:443 或 [::]:443（* 表示同时覆盖 v4/v6）；只有 0.0.0.0:443 说明 IPv6 没监听上。

从外部各自测一次连通性：

# 测 IPv4
curl -4 -sk --max-time 10 https://192.227.236.209:443/ -H "Host: www.colocrossing.com" -o /dev/null -w "IPv4: %{http_code}\n"

# 测 IPv6（地址要加中括号）
curl -6 -sk --max-time 10 "https://[2001:db8::1]:443/" -H "Host: www.colocrossing.com" -o /dev/null -w "IPv6: %{http_code}\n"

两条都返回 301（cloudflare 的真实跳转）就是双栈都通了。

⚠️ curl 测 IPv6 时地址必须加中括号，写成 https://2001:db8::1:443/ 会被解析成域名，报错。

客户端怎么用 IPv6 链接

  • 点链接：和 IPv4 一样，直接点 tme_url，Telegram 自动处理
  • 手动填：Server 栏直接填 IPv6 地址，不要加中括号（Telegram 输入框不需要），如 2001:db8::1
  • 给别人时给哪个：IPv4 链接兼容性最好（几乎所有网络都能连），IPv6 链接只有对方网络支持 IPv6 时才能用。不确定就给 IPv4 那条，或者两条都给让对方自己试

五、动态 IP：能用 DDNS 域名吗？

能。 家宽自建、IP 会变的场景可以完全靠 DDNS 域名跑起来，但要分清两层：服务端不认域名，客户端认域名。

mtg 服务端：三处都只收字面 IP（实测报错）

你想填域名的地方 结果 报错原文
bind-to = "proxy.example.com:3128" ❌ 拒绝 cannot parse a config: host is not an IP address: proxy.example.com:3128
public-ipv4 = "proxy.example.com" ❌ 拒绝 cannot parse a config: incorret ip proxy.example.com（作者拼写错误，原文如此）
mtg access -i proxy.example.com ❌ 拒绝 --ipv4: invalid IP address: proxy.example.com

但这三处都不影响你用 DDNS，因为它们的作用根本不是「告诉别人怎么找到你」：

  • bind-to 是本机监听地址，填 0.0.0.0:端口 或 [::]:端口 就行，它跟你的公网地址无关，本来就不需要填域名
  • public-ipv4 / access -i 只是让 mtg 生成分享链接时往 server 字段里填的值，纯粹是个字符串来源。动态 IP 用户直接别用 mtg access，自己拼链接就完事了

Telegram 客户端：认域名，且各平台一致

这是关键。有三处官方源码/文档证据：

证据一：TDLib 官方接口注释（iOS 官方客户端和大量第三方客户端的核心库）

文件 td/generate/scheme/td_api.tl：

//@server Proxy server domain or IP address
//@port Proxy server port
//@type Type of the proxy
proxy server:string port:int32 type:ProxyType = Proxy;

官方注释明写 domain or IP address。

证据二：Telegram Android 内置 DNS 解析兜底

文件 TMessagesProj/jni/tgnet/ConnectionSocket.cpp，连代理时先试着把地址当 IP 字面量解析，不是 IP 就走 DNS：

struct hostent *he;
if ((he = gethostbyname(proxyAddress->c_str())) == nullptr) {
    DEBUG_E("connection(%p) can't resolve host %s address", ...);

证据三：Telegram Desktop 有专门的域名解析分支

文件 Telegram/SourceFiles/mtproto/mtproto_proxy_data.cpp：

bool ProxyData::tryCustomResolve() const {
	static const auto RegExp = QRegularExpression(
		QStringLiteral("^\\d+\\.\\d+\\.\\d+\\.\\d+$")
	);
	return (type == Type::Socks5 || type == Type::Mtproto)
		&& !qthelp::is_ipv6(host)
		&& !RegExp.match(host).hasMatch();
}

逻辑是：host 既不是 IPv4 也不是 IPv6 字面量（也就是域名）时，对 MTProto / SOCKS5 代理触发自定义解析流程。Desktop 甚至用自己的 DoH 通道解析，抗污染。

结论：Android / iOS / Desktop 全都支持域名，没有平台差异。

具体怎么配

服务端配置：完全不用管域名，照常写就行：

secret = "ee4a7e409b8984becd8117b5729e08e78f7777772e636f6c6f63726f7373696e672e636f6d"
bind-to = "0.0.0.0:443"

[network]
dns = "https://223.5.5.5"

双栈的话：

bind-to = "[::]:443"
prefer-ip = "prefer-ipv4"

注意：动态 IP 场景别写 public-ipv4 / public-ipv6，写死了 IP 一变就是错的，反而误导。

链接自己拼，server 位置直接填你的 DDNS 域名：

https://t.me/proxy?server=proxy.example.com&port=443&secret=ee4a7e409b8984becd8117b5729e08e78f7777772e636f6c6f63726f7373696e672e636f6d

这条链接永久有效，IP 变了也不用换 —— 客户端每次重连都会重新解析域名。

手动填也一样，客户端 Server 栏直接填域名：

字段 填什么
Server / 服务器 proxy.example.com（你的 DDNS 域名）
Port / 端口 443
Secret / 密钥 你的 ee... 密钥

DDNS 场景的注意事项

⚠️ 1. Desktop 端有解析缓存，IP 刚变时可能要手动重连一次

Telegram Desktop 解析完域名会把结果存进 resolvedIPs 缓存。IP 刚跳变的那几分钟，桌面端可能还在连旧 IP。解法：在代理设置里把该代理关掉再打开（或切换一次代理），强制重新解析。手机端一般重连就会自己刷新。

⚠️ 2. DDNS 更新有延迟，TTL 要调小

DDNS 客户端检测到 IP 变化 → 更新 DNS 记录 → 各地 DNS 缓存过期，整个链条有延迟。把域名的 TTL 设成 60 秒（Cloudflare 免费版可设 1 分钟 / Auto），能把中断时间压到最短。TTL 留默认的 3600 秒，IP 变了最坏要等一小时。

⚠️ 3. 用 Cloudflare 做 DDNS 的话，那条记录必须关掉小云朵（DNS only）

Cloudflare 橙色云朵（Proxied）只代理 HTTP/HTTPS 流量，MTProto 走不通，而且开代理后域名解析到的是 Cloudflare 的 IP，不是你家的。这条 DNS 记录必须设成灰色云朵（DNS only / 仅 DNS）。

⚠️ 4. 域名也能顺带当伪装域名用吗？不行

generate-secret 后面跟的伪装域名要选一个大站（www.colocrossing.com 之类），不能填你自己的 DDNS 域名。原因：域名前置要求 mtg 能把探测请求转给那个真实网站并返回像样的响应，填你自己的域名等于自己转给自己，伪装直接失效。这两个域名是两回事，别混：

用途 填什么
客户端连你用的地址（链接 server 字段） 你的 DDNS 域名
FakeTLS 伪装域名（密钥里编码的那个） 与你 IP 归属匹配的大站域名

⚠️ 5. 家宽自建的两个额外拦路虎

这跟 mtg 无关，但动态 IP 通常意味着家宽，得先确认：

  • 有没有公网 IP——很多宽带是大内网（NAT），根本没有独立公网 IP，端口转发做不了。查法：路由器 WAN 口显示的 IP 和 curl -s ifconfig.co 的结果一致才是真公网 IP。不一致就是运营商 NAT，得打电话要公网 IP，或者改用有固定 IP 的中转
  • 端口是否被封——家宽的 80 / 443 常被运营商封禁。443 连不通就换个高位端口（如 27777），代价是伪装效果打折（TLS 走非 443 端口本身是异常信号）

怎么快速判断自己是不是大内网：

# 路由器 WAN 口 IP（登录路由器管理页看），和下面这条对比
curl -s ifconfig.co

ifconfig.co 返回的是 100.64.x.x ~ 100.127.x.x 这个段的话，那是运营商级 NAT 的保留地址，你没有公网 IP。

DDNS 方案 vs 脚本更新链接

如果你的环境不适合 DDNS（比如没公网 IP），备选是脚本定时检测 IP 变化并重新生成链接推送给自己，但这样每次 IP 变了所有用户都得重新加代理，体验很差。能用 DDNS 就用 DDNS。
